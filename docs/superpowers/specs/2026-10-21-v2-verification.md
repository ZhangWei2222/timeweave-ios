## 独立审查与修复

完成一次独立上下文整体代码审查。初始结果：0 Critical、3 Important、1 Minor。重要问题全部以回归测试修复：

1. `Server.Serve` 返回时未等待 `Shutdown`，可能截断请求/日志。现在服务拥有关闭 goroutine 和活动 Handler 的完整生命周期，退出前等待收尾；超时后取消请求并关闭连接。
2. Go 用本地时刻 `AddDate` 推进，午夜夏令时可能生成错误日界。现在以独立日历日期推进，并定位各日第一个真实时刻。两端共同验证 Santiago 跳过午夜的 1380 分钟日和 Havana 重复午夜的 1500 分钟日。
3. iOS 按扩展字素簇计分类名长度，Go 按码点计数导致合法 emoji 被拒绝。现在 Go 接受已有合法名称，整体请求仍受 64 KiB 约束。
4. 大小写别名可能绕过 null 检查。虽初审列为 Minor，执行时按公开契约正确性升级为 Important 并修复：每个对象检查精确字段集合。

另在实现过程中用失败测试复现供应商错误正文回显凭据的可能性，改为仅记录上游 HTTP 状态码。服务公开错误继续映射为固定中文文案。

所有修复后重新执行 Go 全量 race 测试、vet、Swift 18 项测试和两套 SDK 构建。无未处理的重要审查项、无延后的 Minor。

## 执行中作出的取舍

- 用户已明确要求计划后直接实现，沿用该授权，没有增加二次计划批准；代价是计划修改在最终交付统一展示。
- 使用现有干净 checkout 的独立功能分支，保持两个仓库绝对路径稳定；代价是 checkout 当前停在功能分支。
- 原生界面控制工具超时后，增加单独、显式执行的 XCUITest scheme；代价是一个小测试 target，无产品测试开关。
- Go 不额外实现 Unicode 字素分段：沿用 iOS 的 24 个可见字符编辑规则，并用请求总大小约束传输；代价是直接 API 客户端可发送比编辑器更长的分类名。
- 将字段大小写别名问题升级并修复：代价是依赖非规范字段名的客户端会收到 400，与公布的契约一致。
- 没有用数值字符串匹配伪装成回答语义验证。必需工具策略只保证模型读取了真实聚合事实，不能数学证明生成文本逐句正确。

## 模型语义的实际限制

首次真实试跑中，模型曾把 `60/60` 错写为“近 99%”，还曾建议排查本产品不存在的自动采集/同步功能。已增加“引用原值、不自行换算、手工补录产品上下文、避免猜测原因、纯文本短回答”等约束，并再次验证真实输出。最后样本的分钟与占比正确，建议已聚焦确认漏记并手工补录。

提示词不能成为真实性保证：最后样本仍可能使用偏重的评价措辞。因此本期可确认“取数、聚合、隐私边界和工具执行正确”，不能声称任意模型解释均正确。UI 已明确已记录时间不代表全部实际活动；后续若要更强的数字保证，应采用结构化发现与事实引用校验，另行设计，不能靠多加几条提示词宣称解决。
