# 计时式添加交互设计

## 意图

将当前“点击添加时间后填写系统表单”的流程替换成用户熟悉的计时式流程，优先对齐参考 App 的操作位置、状态变化、点击次数和反馈方式，降低长期使用者的迁移成本。

## 目标

- 记录页底部常驻“开始／结束”操作条。
- 点击开始后立刻持续计时，并用吸底状态卡展示开始时间和实时时长。
- 点击结束后停止计时，打开底部确认面板；用户可调整起止时间、选择分类、填写备注后保存。
- 确认面板由页面内 SwiftUI 视图自绘并自行控制遮罩、层级和进出场动画，不使用系统 `sheet` 或 `Form` 外观。
- 运行中的计时持久化，App 切后台或被系统回收后仍能继续按真实时间计算。
- 编辑已有记录复用同一个底部编辑面板。

## 非目标

- 不实现通知、灵动岛、Live Activity、桌面组件或后台常驻任务。
- 不改变现有记录格式、统计口径、重叠规则和跨日规则。
- 不逐像素复制参考 App 的旧视觉风格。

## 交互状态

1. **空闲**：底部显示一个胶囊操作条；“开始”可用，“结束”不可用。
2. **计时中**：点击开始后保存开始时间，底部改为运行卡片；卡片按秒显示当前时长，提供取消和结束。
3. **待确认**：点击结束后清除运行态并弹出编辑面板；结束时间冻结为点击结束的时刻。
4. **编辑**：自绘面板顶部并排显示开始时间、时长、结束时间；中部用分类胶囊选择分类；底部填写备注并确认。同日记录默认折叠日期控件，跨日记录自动展开。
5. **完成/放弃**：保存成功后刷新当日分布；取消确认只放弃未保存草稿。运行卡片上的取消需要二次确认，避免误触丢失长时间计时。

历史补录通过“开始后立即结束，再调整起止时间”完成。少于一分钟的有效记录允许保存，并继续使用现有“不足 1 分钟”展示规则。

## 约束与异常

- 同一时间只能存在一个运行中的计时。
- 保存仍要求结束晚于开始、结束不晚于当前时间、分类有效且不与现有记录重叠。
- 停止计时失败时保留运行状态并显示错误；保存失败时保留编辑面板和用户输入。
- 正在计时时可切换日期，但运行卡片始终可见；停止后编辑器以计时的真实日期为准。
- 计时依赖时间戳，不依赖后台定时器，因此 App 暂停不会丢失时长。

## 方案比较

### 采用：领域状态持久化 + SwiftUI 吸底状态机

将运行开始时间作为账本中的可选领域状态持久化；`DayView` 只负责展示状态和发起动作。优点是重启恢复可靠、无需后台任务、状态来源唯一；代价是账本模型增加一个向后兼容字段。

### 未采用：仅在 View 中保存计时状态

实现最少，但切后台重建视图或 App 被终止时会丢失计时，与“长期使用的记录工具”目标冲突。

### 未采用：独立计时器文件或 UserDefaults

可以工作，但会形成账本和计时状态两套持久化事务，增加恢复时的不一致路径；当前数据规模下没有收益。

## 验收

- 点击开始后出现运行卡，时长持续增加；重启后仍从原开始时间计算。
- 点击结束后进入确认编辑，起止时间与实际点击时刻一致。
- 未选择分类、未来结束时间或重叠时间无法保存，并显示原有领域错误。
- 保存、编辑和删除后，日环图、列表和统计保持一致。
- VoiceOver 能读出开始、结束、取消、时长、分类和保存动作；动态字体不会遮挡关键操作。
